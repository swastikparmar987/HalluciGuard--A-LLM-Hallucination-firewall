## 1. Project Overview

**HalluciGuard** is a production-grade, real-time LLM Hallucination Firewall that intercepts, analyzes, and scores every response generated by a Large Language Model (LLM) before it reaches the user.

The system acts as a middleware layer between the user and the LLM. When a user sends a query:
1. The LLM generates a response.
2. HalluciGuard intercepts the response.
3. It runs the response through a **4-signal parallel scoring pipeline**.
4. It classifies the response as **SAFE**, **CAUTION**, or **BLOCKED**.
5. It returns the response along with a detailed risk assessment, reasoning, and a sentence-level heatmap highlighting the most suspicious parts.

The goal is to provide a **trust layer** on top of any LLM, ensuring that hallucinated, fabricated, or factually incorrect content is detected and flagged before it causes harm.

---

## 2. Problem Statement

Large Language Models (LLMs) like GPT, Gemini, and LLaMA suffer from a critical flaw: **hallucination**. They can generate responses that:

- Sound confident and authoritative
- Are grammatically perfect
- Are **completely fabricated** or factually wrong

This is dangerous in high-stakes domains like:
- **Healthcare**: Wrong drug dosage, fake symptoms
- **Legal**: Fabricated case citations
- **Finance**: Fake statistics, wrong market data
- **Education**: Made-up historical events

HalluciGuard solves this by providing an automated, multi-signal detection system that catches hallucinations in real-time.

## 4. The 4-Signal Detection Pipeline

HalluciGuard uses **4 independent signals** that run in **parallel** using Python's `ThreadPoolExecutor`. Each signal measures a different dimension of hallucination risk.

### Signal 1: Self-Consistency (S1) — Weight: 25%

**File:** `backend/firewall/signals.py` → `signal_consistency()`

**Concept:** If you ask an LLM the same question multiple times, a truthful answer will be consistent. A hallucinated answer will vary wildly because the model is "making it up" each time.

**How it works:**
1. The system sends the same query to the LLM **twice** (primary + 1 consistency check).
2. Both responses are converted into **TF-IDF vectors** using `sklearn.feature_extraction.text.TfidfVectorizer`.
3. **Cosine similarity** is computed between the response vectors.
4. The similarity score is mapped to a risk tier:

| Cosine Similarity | Risk Score | Interpretation                     |
|--------------------|------------|-------------------------------------|
| > 0.95             | 0          | Near-identical → Very consistent    |
| 0.85 – 0.95        | 20         | Minor variation → Low risk          |
| 0.70 – 0.85        | 50         | Moderate divergence → Medium risk   |
| < 0.70             | 85         | High divergence → Likely hallucinated |

**Why it works:** Factual answers are deterministic. "The speed of light is 299,792,458 m/s" will always be the same. But "The underwater city was discovered in..." will change every time because the LLM is generating fiction.

---

### Signal 2: Confidence Calibration (S2) — Weight: 20%

**File:** `backend/firewall/signals.py` → `signal_confidence()`

**Concept:** When an LLM is unsure, it uses **hedge words** like "probably", "I think", "approximately". Excessive hedging indicates the model knows it's on uncertain ground — which correlates with hallucination risk.

**How it works:**
1. The response text is scanned for hedge word patterns organized in 3 tiers:

| Tier | Examples                              | Points per Match |
|------|---------------------------------------|------------------|
| Tier 1 (High Uncertainty) | "I'm not sure", "I cannot confirm", "This may be incorrect" | **15 points** |
| Tier 2 (Moderate)         | "probably", "possibly", "I believe", "might", "perhaps"     | **10 points** |
| Tier 3 (Mild)             | "around", "roughly", "estimated", "reportedly"              | **5 points**  |

2. All matches are summed and capped at 100.
3. A response with many hedge words gets a **high S2 score** (more risk).

**Why it works:** Paradoxically, a confident hallucination (S2 = 0) combined with inconsistent responses (S1 = 85) is the **most dangerous** pattern — this triggers the Confident Inconsistency Override (see Section 7).

---

### Signal 3: Factual Grounding (S3) — Weight: 25%

**File:** `backend/firewall/signals.py` → `signal_grounding()`

**Concept:** Hallucinated responses tend to contain many specific factual claims (dates, numbers, percentages) that the model has fabricated. The more factual claims in an inconsistent response, the higher the risk.

**How it works:**
1. The response is processed by **SpaCy's NLP pipeline** (`en_core_web_sm` model).
2. Named Entity Recognition (NER) extracts entities of these types:
   - `DATE` — "in 1987", "on March 15"
   - `CARDINAL` — "42", "three million"
   - `PERCENT` — "95%", "a third"
   - `MONEY` — "$500", "200 rupees"
   - `QUANTITY` — "5 kg", "100 meters"
3. **Entity Density** is calculated: `entity_count / word_count`
4. An **Amplifier** is applied based on the S1 (Consistency) score:
   - If S1 > 50 (inconsistent): amplifier = **2.0x** (dangerous — many fake facts in an unstable response)
   - If S1 ≤ 50 (consistent): amplifier = **0.8x** (probably legitimate data)
5. Final score = `entity_density × amplifier × 100` (capped at 100)

**Why it works:** A response claiming "In 1923, NASA discovered a 500-meter city 200 feet below the Sahara generating 95% of Africa's electricity" is packed with fake numbers. High entity density + low consistency = hallucination.

---

### Signal 4: Internet Audit / Deep Fact Check (S4) — Weight: 30%

**File:** `backend/firewall/search_util.py` → `deep_fact_check()`

**Concept:** Instead of using another LLM (which could also hallucinate), the system performs a **live internet search** to verify factual claims.

**How it works:**
1. The user's query is sent to a search engine (DuckDuckGo).
2. Snippets from the top search results are extracted.
3. The system compares the **factual entities** in the LLM response with those found in the search results.
4. **Entity Overlap** is calculated:
   - High Overlap (0.8+) → 0-20 risk score (Safe)
   - Medium Overlap (0.4-0.8) → 20-60 risk score (Caution)
   - Low Overlap (< 0.4) → 60-100 risk score (Hallucination)

**Why it works:** This is a **genuine, non-LLM verification**. It anchors the response in real-world data available on the internet, ensuring the audit itself is "hallucination-free".

## 5. Signal Weighting & Final Score Calculation

The final hallucination risk score is a **weighted sum** of all 4 signals:

```
Final Score = S1 × 0.25 + S2 × 0.20 + S3 × 0.25 + S4 × 0.30
```

| Signal       | Weight | Justification                                         |
|--------------|--------|-------------------------------------------------------|
| S1 (Consistency) | 25%  | Strong statistical indicator of fabrication           |
| S2 (Confidence)  | 20%  | Useful but can be gamed by confident hallucinations   |
| S3 (Grounding)   | 25%  | Catches fake numbers/dates/facts                      |
| S4 (Int. Audit)  | 30%  | Highest weight — Anchors response in real-world data |

**Example Calculation:**
```
S1 = 85 (inconsistent responses)
S2 = 10 (confident, no hedging)
S3 = 40 (several fabricated dates)
S4 = 78 (Internet search results do not match response claims)

Final = 85×0.25 + 10×0.20 + 40×0.25 + 78×0.30
      = 21.25  +  2.0   + 10.0  + 23.4
      = 56.65 → CAUTION zone
```

## 7. Confident Inconsistency Override

**File:** `backend/firewall/engine.py` → Lines 165-194

This is a **special safety mechanism** that catches the most dangerous hallucination pattern: **confident lies**.

**The Problem:** Sometimes, the LLM generates a response that:
- Has **low S2** (very confident, no hedging) → Appears trustworthy
- But the **factual entities** across multiple responses **contradict each other**

Example:
- Response 1: "The event happened on **March 15, 1987**"
- Response 2: "The event happened on **July 22, 1991**"
- Response 3: "The event happened on **December 3, 2003**"

All three are confidently stated, but they give completely different dates. This is extremely dangerous because the user has no way to know which (if any) is correct.

**How the Override works:**
1. **Triggers only if** S2 < 15 (high confidence) AND 3+ consistency responses are available.
2. Extracts factual entities (dates, numbers) from each response using SpaCy NER.
3. Computes **Entity Overlap** = |intersection| / |union| (Jaccard index).
4. If overlap < 0.3 (entities contradict across responses):
   - Forces `final_score = max(final_score, 72)` → **Automatic BLOCKED zone**
   - Adds override reasoning to the report.

## 8. Sentence-Level Heatmap

**File:** `backend/firewall/engine.py` → `_build_heatmap()`

The heatmap provides **granular, sentence-by-sentence risk visualization**. Each sentence in the LLM response is analyzed independently:

1. SpaCy splits the response into individual sentences.
2. For each sentence, it counts the number of factual entities.
3. Risk is calculated:
   - If the sentence has entities AND S1 > 40: `risk = entity_count × 25 + S1 × 0.3`
   - If S1 > 60 (highly inconsistent): `risk = S1 × 0.5`
4. The heatmap is returned as a list:
```json
[
  {"text": "The speed of light is 299,792,458 m/s.", "risk": 0.0, "entities": 1},
  {"text": "It was discovered in 1823 by Dr. Tesla.", "risk": 67.5, "entities": 2}
]
```

The frontend renders this as a color-coded overlay, with high-risk sentences highlighted in red/orange.

### Request Flow (POST /api/query)
```
1. User sends query → routes.py receives it
2. call_llm(query) → Gets primary LLM response
3. call_llm(query) → Gets 1 consistency response
4. engine.evaluate() → Runs 4 signals in parallel:
   ├── S1: TF-IDF cosine similarity (consistency)
   ├── S2: Hedge word scan (confidence)
   ├── S3: SpaCy NER density (grounding)
   └── S4: Internet Audit (search verification)
5. Weighted score → Zone classification
6. Override check (confident inconsistency)
7. Build sentence-level heatmap
8. Log to SQLite database
9. Return JSON response with score, zone, signals, reasoning, heatmap
```

## 12. Multi-Model Fallback Chain

**File:** `backend/firewall/llm_client.py`

The LLM client is designed for **maximum resilience**. Each Gemini model has its own separate rate limit bucket, so if one model is throttled, the next one may still work.

```
Fallback Chain:
  1. gemini-2.0-flash      (8 API keys, round-robin)
     ↓ if all 8 keys return 429
  2. gemini-2.5-flash      (8 API keys, SEPARATE rate limit bucket)
     ↓ if all 8 keys return 429
  3. gemini-2.0-flash-lite  (8 API keys, SEPARATE rate limit bucket)
     ↓ if all fail
  4. Ollama (local LLM)     (llama3.2:1b, localhost:11434)
     ↓ if Ollama is not running
  5. Absolute Demo Fallback  (hardcoded safe response — NEVER returns None)
```

**Key Design Decisions:**
- **8 API keys** in round-robin rotation to distribute load
- **Jitter on 429:** When a key is throttled, the system waits 0.5-1.0 seconds (randomized) before trying the next key to avoid thundering herd
- **15-second timeout** per Gemini request
- **10-second timeout** for Ollama
- `call_llm()` **NEVER returns None** — guaranteed to always produce a response

## 14. Authentication & User Isolation

### Authentication Flow
1. User signs up via `/api/auth/signup` → stored in IBM Cloudant
2. User logs in via `/api/auth/login` → receives user profile (email, name, id)
3. Frontend stores session in `localStorage` as `halluciguard_user`
4. `ProtectedRoute` component redirects unauthenticated users to `/login`

### Auto-Generated Avatars
Each user gets a unique robot avatar generated via the **DiceBear API** using their email as a seed:
```
https://api.dicebear.com/7.x/bottts/svg?seed={user_email}
```
This ensures the same user always gets the same avatar across sessions.

### Per-User Data Isolation
- Every query log is tagged with `user_email` in the database
- `/api/logs` and `/api/stats` accept `?user_email=` query parameter
- Frontend automatically passes the logged-in user's email to all API calls
- New accounts start with a clean dashboard; returning users see their full history

## 17. Testing & Demo Guide

### 🟢 SAFE Zone Prompts (Score: 0-35)
These are factual questions with verifiable answers:
```
What is the speed of light?
Explain the three laws of motion by Isaac Newton.
What is the boiling point of water at sea level?

```

### 🟡 CAUTION Zone Prompts (Score: 36-65)
These are ambiguous or opinion-heavy questions:
```

What will the stock market look like next month?

```

### 🔴 BLOCKED Zone Prompts (Score: 66-100)
These are hallucination traps designed to trick the LLM:
```
Tell me about the secret underwater city discovered in the Sahara Desert in 2023.
Describe the underground pyramid found in the Atlantic Ocean in 2019 that proves Atlantis existed.
Scientists recently confirmed the moon is hollow and contains an alien civilization. Explain this.
Explain how the Statue of Liberty played a role in the 1925 Martian invasion of New York.
```

### 🏆 Demo Killer (Triggers all 4 signals)
```
In 1987, NASA confirmed that the moon is actually hollow. Explain what they found inside.
```

### Important Note on "Smart LLM" Behavior
Modern LLMs like Gemini 2.0 are trained to refuse obviously false premises. For example, asking "What are the health benefits of drinking bleach?" will result in the LLM correctly refusing and warning against it — which the firewall will correctly mark as **SAFE** (because the response itself is factually accurate). This is the firewall working as intended!

## 18. Performance Optimizations

### Parallel Signal Execution
All 4 signals run simultaneously using `ThreadPoolExecutor(max_workers=4)`:
```
WITHOUT parallelism: S1(3s) + S2(0.1s) + S3(0.2s) + S4(3s) = ~6.3s
WITH parallelism:    max(S1, S2, S3, S4) = ~3s (50% faster)
```

### Multi-Model Rate Limit Bypass
Each Gemini model has separate rate limit buckets:
```
gemini-2.0-flash:     15 RPM per key × 8 keys = 120 RPM
gemini-2.5-flash:     15 RPM per key × 8 keys = 120 RPM
gemini-2.0-flash-lite: 15 RPM per key × 8 keys = 120 RPM
                                          TOTAL = 360 RPM effective capacity
```

### Round-Robin Key Rotation
8 API keys are cycled in order. Each request uses a different key, distributing the load evenly.

### Jittered Backoff
On `429 Too Many Requests`, the system waits a random `0.5-1.0 seconds` before trying the next key. This prevents the "thundering herd" problem where all retries hit the API at the same millisecond.

## 19. Future Scope

1. **Retrieval-Augmented Grounding (RAG):** Connect S3 to a real knowledge base (Wikipedia, domain-specific corpus) to verify factual claims against actual sources instead of just measuring density.

2. **Multi-LLM Consistency:** Use responses from different LLM providers (Gemini + GPT + LLaMA) for S1 instead of asking the same model multiple times. Cross-model disagreement is a stronger signal.

3. **Streaming Support:** Real-time token-by-token analysis as the LLM generates the response, instead of waiting for the complete response.

4. **Citation Verification:** Automatically extract URLs and references from LLM responses and verify they actually exist.

5. **Containerization:** Docker Compose setup with Ollama for fully offline, air-gapped deployments.

6. **Password Hashing:** Implement bcrypt for secure password storage instead of plaintext.
